# 当一个 AI agent 雇用另一个 agent：先检查工作，再付钱

*Edward Zhou · [云书 AI](https://yunshu.ai) · 2026 年 10 月 12 日 · [English](2026-10-agent-hires-agent.md)*

在[上一篇](2026-10-agent-pays-safely-zh.md)里，AI agent 从一个把规则写进智能合约的钱包里为 API 调用付费。这之所以行得通，是因为调用 API 是即时的：付了钱，答案马上回来，事情就结束了。

雇用另一个 agent 就不一样了。工作是之后才交付的，可能做错，也可能根本不交。所以雇主 agent 还需要一样东西：**在检查完工作之前，先把钱托管起来**，而且不能因此在原有的支出规则上开一个口子。

我把这部分加进了演示。每隔几小时，`research-bot-01` 会通过 Base Sepolia 上的一个托管合约雇用 `worker-bot-01`，做一件小事：求三个价格的平均值。所有任务都能在 [demo.yunshu.ai/zh/](https://demo.yunshu.ai/zh/) 上看到，代码在 [GitHub](https://github.com/edxzh/agent-wallet)。下面是四个关键做法，以及过程中踩到的坑。

## 一、钱放进托管，但规则必须"看得见"worker

雇主 agent 把报酬付进 `JobEscrow` 合约，走的是和普通付款同一个 `authorize` 调用，所以单笔上限、每日预算、任务预算都照样生效。

我最初的设计有个漏洞，直到自己审查时才发现：钱包的**收款方规则**（白名单，以及"只有信誉足够好才付给陌生服务"）从头到尾只看到一个收款方，就是托管合约。运营者一旦把托管合约加进白名单，agent 就可以"雇用"任何人。在[试一试页面](https://demo.yunshu.ai/zh/try/)上，"付给陌生人"会被拒绝；可"雇用陌生人"却能通过。

修复的办法不需要改钱包：托管合约在收钱之前，先用钱包检查每个收款方时的同一个问题去问雇主的钱包："我可以付钱给这个 worker 吗？"（`checkPayee`）。答案是"不行"，托管合约就记一条拒绝事件，一分钱都不动。

这个教训有普遍意义：**在 agent 和收款方之间加一个合约时，要确认你的规则实际看到的是哪个地址。**

## 二、worker 把答案的哈希上链，雇主来检查

worker 交付结果，并把结果的哈希写到链上。雇主拿到文本后，先核对它和哈希是否一致，再自己验算答案。每次运行还会公开任务和答案，任何人都可以自己算一遍两个哈希和平均值。

有些任务是故意做错的。在[这一单](https://sepolia.basescan.org/tx/0xb6f19a8b19e706080bbb40f96f8590bae0d57350713249bc189174d0adf43fbd)里，worker 有一个看起来很真实的 bug：只平均了前两个价格，答成了 1044.81，正确答案是 1043.46。雇主的检查发现了错误，并[拒绝了这次交付](https://sepolia.basescan.org/tx/0x598235f201eae274cd06f3f31449198c15f378765a8ae19a5b37151d31768172)。而一分钟前那一单认真的任务，检查通过，雇主[接受了交付](https://sepolia.basescan.org/tx/0x01ffd5c138d8b6630146509bb6245693f8d4cb43bef324e99efc01d53c3b1fa1)，worker 收到了报酬。

## 三、争议要由雇主以外的人来裁决

被拒绝的交付会进入**争议**，钱留在托管合约里不动。只有这一单的裁决人可以决定付给 worker 还是退给雇主，而托管合约要求裁决人必须是雇主钱包的**运营者**。最初的版本里，雇主 agent 可以把自己指定为裁决人，那就等于自己审自己的案子。worker 也不能当裁决人。

也要说清楚局限：在这个演示里，两个钱包由同一个人运营，所以裁决人并不独立于 worker。真实的市场需要由别人运营的 worker，或者第三方裁决人。

## 四、无论谁沉默，任务都会结束

一个可能把钱永远冻住的托管，比没有托管更糟。所以每个状态都有截止时间，过期之后任何人都可以触发后续：

- worker 没按时交付：退款给雇主；
- 雇主没按时回应：付款给 worker；
- 裁决人没按时裁决：退款给雇主。

每个截止时间只有一条分界线，任何时刻都不会出现"既能操作、又能超时"的情况。单元测试逐一检查每条分界线，模糊测试在每个时间窗口里随机尝试一千个时刻。

安全审查还发现了一种不太明显的冻结方式：USDC 可以把地址加入**黑名单**。worker 一旦被拉黑就收不了钱，付款会回滚，而当时关闭任务的每一条路径（包括超时）都会跟着回滚。现在托管合约先关闭任务、再付款；如果代币拒绝这笔付款，金额就记为"待付"，等代币允许之后，任何人都可以把钱转过去。我在本地复制的链上，用 Circle 真实代币自己的黑名单权限测试过这一点。

## 让我意外的几件事

- **一次拒绝可能泄露一个签名。** 托管合约拒绝某个 worker 时，带着雇主转账签名的那笔调用仍然留在链上，任何人都可以把这个签名直接提交出去。钱偷不走（它只能从钱包转进托管合约），但总归不干净。所以现在 agent 会在签名**之前**，先用一次免费的只读调用问钱包这个 worker 能不能付；托管合约里的检查则作为兜底，防的是有 bug 或被攻破的 agent。
- **按时间段命名，调度就不需要状态。** 每一单的编号由它所在的 6 小时时段和任务类型算出来，所以每次运行都不需要状态文件：同一时段重跑不会重复雇用，下一次运行也能找到上一次的任务，替它们处理超时。
- **本地分叉链不等于真链。** 在本地复制的 Base Sepolia 上演练时暴露了两个差别：本地链只在有交易时才出块，所以"等待 3 个确认"永远等不到；它的 gas 价格也比真实网络高得多，在 Base Sepolia 上轻松付得起的交易，在本地却因为余额不足而失败。在相信演练结果之前，最好先知道这些。
