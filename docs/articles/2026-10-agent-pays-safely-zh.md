# 让 AI agent 自己付钱，又不让它乱花钱

*Edward Zhou · [云书 AI](https://yunshu.ai) · 2026 年 10 月 11 日 · [English](2026-10-agent-pays-safely.md)*

AI agent 已经开始自己买东西了：调一次 API、买一份数据。[x402](https://www.x402.org/) 让这件事变得很简单：服务端返回 `402 Payment Required` 并报价，agent 签一笔付款，请求就通过了。但 x402 没有回答每个团队接下来都会问的问题：**怎么防止 agent 花超了，或者把钱付给了不该付的人？**

我做了一个小而公开的回答：一个把支出规则写进智能合约的 agent 钱包。它运行在 Base Sepolia 测试网上，在线演示在 [demo.yunshu.ai/zh/](https://demo.yunshu.ai/zh/)，代码在 [GitHub](https://github.com/edxzh/agent-wallet)。下面是让它成立的四个想法，以及过程中让我意外的几件事。

## 一、钱在合约里，agent 手里只有一把钥匙

钱不在 agent 手上，而在一个 `PolicyWallet` 合约里。规则由运营者（我）设定：单笔上限、每日预算（UTC 零点重置）、按任务的预算、收款白名单，以及一个暂停开关。

agent 的私钥只能做一件事：请求钱包**授权**一笔付款。它改不了任何规则。就算 agent 的私钥被盗，损失也不会超过规则允许的范围，运营者还可以随时暂停钱包。

## 二、用合约钱包走标准的 x402 付款

x402 在 EVM 链上的标准 `exact` 方案基于 EIP-3009：付款方签一笔 `TransferWithAuthorization`，由 *facilitator*（结算方）提交给 USDC 合约。通常付款方是普通账户；而这里付款方是钱包合约，合约自己是没法签名的。

解决办法是 **ERC-1271**，也就是合约签名的标准：

1. agent 用自己的私钥签名，但 `from` 填的是钱包地址；
2. USDC 发现付款方是合约，就去问它 `isValidSignature(…)`；
3. 钱包**只**对"已经授权过、并由自己的 agent 签名"的付款说"有效"。

所以 `authorize` 是唯一的关卡：所有规则都在这里、在链上、在签名之前检查。

我没有想当然。正式写钱包之前，我先部署了一个 37 行的测试合约，通过公开的 x402.org facilitator 去付一个真实的 x402 接口，两笔都结算成功了（[其中一笔](https://sepolia.basescan.org/tx/0xe733dc33b67f89295fd6c8c04e8c375356aa1c06562e44456faaa7f3f54b5005)）。一个下午、一次实测，整个设计就建立在证据上，而不是对文档的理解上。还有个意外的好处：结算的 gas 由 facilitator 支付，agent 只需要为自己的 `authorize` 调用付 gas。

## 三、拒绝是一条公开记录，而不是一个报错

合约说"不"的常见做法是 revert（回滚）。但回滚的交易不会留下任何痕迹，而这个钱包的意义恰恰在于：**被拦下的付款也要看得见**。

所以 `authorize` 从不因为规则而回滚。它会发出一个 `PaymentRefused` 事件，附带且只附带一个原因，然后返回 `false`。可能的原因有：超出单笔上限、超出每日预算、超出任务预算、收款方不在白名单、钱包已暂停、余额不足、金额无效。钱一分没动，任何人都能在 BaseScan 上核对。看板会把每一条拒绝用大白话展示出来，和成功的付款放在一起。

## 四、陌生的服务，要有你信任的人担保才付

白名单安全，但不够灵活。演示的第二部分让钱包也能付款给从没被告知过的服务，前提是它们挣到了足够好的声誉。用的是 Base Sepolia 上公开的 [ERC-8004](https://eips.ethereum.org/EIPS/eip-8004) 身份与声誉登记合约。

标准里的两个细节，几乎构成了全部的安全性：

- **声誉必须通过一份评价者名单来读取。** ERC-8004 的汇总函数要求你指定"谁的评价算数"，其他人刷的好评根本不计入。演示中的规则是"来自至少 3 位可信评价者、平均分 ≥ 70"，这一检查同样在链上的 `authorize` 里完成。
- **身份和收款地址绑定。** 服务声称自己拥有某个 ERC-8004 身份，钱包会核对该身份登记的收款地址是否就是这次的收款方。冒用一个好评如潮的身份、却要求把钱打到别处的冒充者，会被直接拒绝。

评价也没法凭空捏造：评价者就是钱包本身，而且只能对**已经结算**的付款评价一次；每条评价都带着那笔付款的 nonce，因此每个评分都对应一笔真实的付款。在看板上，你可以看到可靠的服务逐渐赢得信任、不稳定的服务失去信任、冒充者每次都被拒之门外。

## 让我意外的几件事

- **公共 RPC 节点会滞后。** 交易刚上链时，`sepolia.base.org` 偶尔会从落后一个区块的节点返回数据；facilitator 也在用自己的节点校验签名。所以现在 agent 在 `authorize` 之后会等几个确认再签名。读状态时要按事件读，或者读回执所在的区块，不要直接读 "latest"。
- **免费服务的限制会反过来塑造设计。** 公共 RPC 每次最多只返回 500 个区块的日志，在 Base 上大约是 16 分钟。所以看板由定时任务生成并提交的快照渲染，只有最近几分钟的数据才实时从链上读取。附带的好处是：关掉 JavaScript 页面照样能看。
- **可升级的登记合约需要"钉住"。** ERC-8004 的登记合约是由第三方运营的可升级合约。因此每次运行前都会先核对它们的实现地址，一旦发生变化，就在付款之前停下来。
